# Jancher — архитектура

## 0. Где я спорю с исходным брифом

Бриф просил не реализовывать идеи молча, а оспаривать. Пять мест, где я предлагаю другое.

### 0.1. «Подгруппы» — не отдельная сущность

В брифе: Группа → Подгруппа → Приложения, три разных понятия.

Предлагаю: **одна сущность `Group` с `parentId`**. Подгруппа — это группа, у которой есть родитель. Ноль дополнительного кода, ноль дублирующихся экранов редактирования, а ограничение глубины живёт в UI-слое (по умолчанию 2 уровня), а не в схеме БД.

Почему это важнее, чем кажется: если подгруппа — отдельный тип, то каждая фича («правила наполнения», «свой layout», «переименовать», «спрятать») пишется дважды. Через полгода они разойдутся в поведении, и это будет видно пользователю.

Опасение из брифа — «не превратить в файловый менеджер» — решается не схемой, а UI: экран редактирования просто не даёт создать третий уровень. Снять ограничение позже — одна строка.

### 0.2. Favorites — не состояние приложения, а группа с ролью

В брифе Favorite стоит в одном ряду с Normal/Archived/Hidden. Это разные по природе вещи:

- **Archived / Hidden** — свойства *приложения*: они отвечают на вопрос «показывать ли его вообще».
- **Favorite** — это *местоположение*: приложение лежит в конкретном контейнере.

Если сделать Favorite булевым флагом приложения, то «несколько списков избранного» (о которых бриф сам же и просит) становятся невозможными без переписывания. Поэтому:

```
Favorites = Group(role = FAVORITES)
```

Обычная группа с системной ролью, ручным порядком, без ограничения на размер. Хочешь второй список избранного — создаёшь вторую группу с той же ролью. Ноль нового кода.

Отсюда же и ответ на «unlimited favorites»: ограничения нет не потому, что мы его сняли, а потому, что его негде было бы завести.

### 0.3. Archived и Hidden — взаимоисключающие, и это правильно

Бриф просит «не делать состояния взаимоисключающими без необходимости». Здесь необходимость есть: «архивировано» и «скрыто» отвечают на один и тот же вопрос (насколько глубоко спрятать), просто с разной силой. Приложение, которое одновременно «в архиве» и «скрыто», не имеет осмысленного поведения — при попытке его показать непонятно, какое правило побеждает.

Поэтому: **одно поле `visibility: VISIBLE | ARCHIVED | HIDDEN`** и отдельно — членство в группах.

| Состояние | В списке групп | В поиске | В архиве | Смысл |
|---|---|---|---|---|
| VISIBLE | да | да | — | обычное |
| ARCHIVED | нет | по настройке (по умолчанию нет) | да | «нужно раз в полгода» |
| HIDDEN | нет | нет | нет | «этого приложения для меня не существует» |

Важно назвать честно: **HIDDEN — это не приватность.** Приложение остаётся в системных настройках, в шторке, в недавних. Лаунчер не может это изменить. Если нужен реальный «скрытый ящик» с биометрией — это отдельная фича с честной оговоркой, что она защищает только от «дай глянуть телефон», и ставится в поздние фазы.

Отдельно: с Android 15 в системе есть **настоящее архивирование** (`PackageInstaller.requestArchive`) — оно удаляет APK, оставляя иконку и данные, и освобождает место. Это другое, чем наш «архив», и их не надо путать. На API 35+ можно предложить пользователю: «убрать из вида» (наш архив) и «архивировать по-настоящему, освободив 1.2 ГБ» (системный API). Хорошая фича на потом.

### 0.4. Ключ приложения — не имя пакета

Легко написать `packageName` и потом месяцами чинить последствия. Правильный ключ:

```
ComponentKey = packageName + "/" + activityClassName + "#" + userSerial
```

Три причины:
- У приложения может быть **несколько launcher-активити** (Termux:API, некоторые игры, эмуляторы, Xiaomi-утилиты). По имени пакета они схлопнутся в одну строку списка.
- **Рабочий профиль** (work profile) — это тот же пакет с другим пользователем. Их надо показывать раздельно и запускать через разные API.
- Пользовательские настройки (архив, кастомное имя, членство в группах) должны **переживать удаление и переустановку** приложения. Значит, они хранятся по `ComponentKey`, а не по автоинкрементному id строки, которая исчезнет при удалении.

### 0.5. Аккордеон + рельс: конфликт, который надо решить в дизайне, а не в коде

Выбранная модель («1+3») содержит скрытое противоречие. Рельс работает как «веду палец — список едет к нужной группе». Аккордеон означает, что высота списка меняется при каждом раскрытии. Если совместить наивно, палец будет попадать не туда, куда целился: пока вёл, содержимое под пальцем уехало.

Решение, которое я предлагаю:

- **Раскрыта всегда ровно одна группа** (эксклюзивный аккордеон). Открывая новую, закрываем предыдущую.
- **Рельс не скроллит список, а выбирает группу.** Ведёшь палец — рядом всплывает крупная «таблетка» с именем группы под пальцем (список при этом неподвижен, ничего не дёргается). Отпустил — группа раскрывается, список анимированно подъезжает так, чтобы её заголовок встал под верхнюю зону.
- Заголовок раскрытой группы **липкий** (sticky), чтобы всегда было видно, где ты находишься.
- Сдвиг пальца влево, не отпуская — рядом с таблеткой выезжает вертикальный список подгрупп. Отпустил на подгруппе — раскрылась она.

Это делает всё одним непрерывным движением большого пальца и убирает дрожание списка. Плюс бонус: при таком поведении рельс не обязан быть пропорционален длине списка, а значит, группы на нём — крупные и удобные цели.

## 1. Модель данных

Источник истины о том, *что установлено* — система (`LauncherApps`). Источник истины о том, *как это организовано* — наша БД. Смешивать нельзя: при переустановке приложения система создаёт всё заново, а организация должна выжить.

### 1.1. Таблицы

```kotlin
// Кеш установленного. Полностью перестраивается из LauncherApps, ничего пользовательского не хранит.
@Entity
data class AppEntity(
    @PrimaryKey val componentKey: String,   // "pkg/class#userSerial"
    val packageName: String,
    val className: String,
    val userSerial: Int,
    val label: String,
    val labelFolded: String,   // нормализовано для поиска: lowercase, без диакритики
    val initials: String,      // "vlc media player" -> "vmp", для поиска по инициалам
    val categoryHint: Int?,    // ApplicationInfo.category, часто -1
    val isSystem: Boolean,
    val firstInstallTime: Long,
    val lastUpdateTime: Long,
)

// Пользовательские свойства приложения. Живут дольше самого приложения.
@Entity
data class AppPrefsEntity(
    @PrimaryKey val componentKey: String,
    val visibility: Visibility = VISIBLE,   // VISIBLE | ARCHIVED | HIDDEN
    val customLabel: String? = null,
    val customIconRef: String? = null,       // ссылка на иконпак или свой файл
    val archivedAt: Long? = null,
)

@Entity
data class GroupEntity(
    @PrimaryKey val id: Long,
    val parentId: Long?,          // null = верхний уровень; иначе подгруппа
    val title: String,
    val position: Int,
    val role: GroupRole,          // NORMAL | FAVORITES | ALL_APPS | ARCHIVE
    val layout: GroupLayout,      // LIST_COMPACT | LIST_COMFORT | GRID | LARGE_BUTTONS
    val sort: GroupSort,          // MANUAL | ALPHA | USAGE | RECENT
    val rule: String?,            // JSON правила, null = только ручной состав
    val showOnRail: Boolean = true,
    val hidden: Boolean = false,
)

// Ребро «приложение ↔ группа». Одно приложение — сколько угодно рёбер.
@Entity(primaryKeys = ["groupId", "componentKey"])
data class GroupMemberEntity(
    val groupId: Long,
    val componentKey: String,
    val kind: MemberKind,     // PINNED (добавлено руками) | EXCLUDED (изъято руками)
    val position: Int,
    val displayOverride: String? = null,  // JSON: своё имя/иконка именно в этой группе
)
```

Ровно это и есть запрошенное «приложение ≠ место в лаунчере»: `AppEntity` — приложение, `GroupMemberEntity` — ссылка на него. Ссылок может быть сколько угодно, `displayOverride` даёт разный вид одного приложения в разных группах.

### 1.2. Как вычисляется состав группы

```
состав(g) = ( применить_правило(g) ∪ PINNED(g) ) \ EXCLUDED(g) \ невидимые
```

Правило — sealed-иерархия, сериализуемая в JSON:

```kotlin
sealed interface GroupRule {
    data class AlphaRange(val from: Char, val to: Char) : GroupRule
    data class Category(val playCategory: Int) : GroupRule
    data class InstalledAfter(val timestamp: Long) : GroupRule
    data object Unassigned : GroupRule     // всё, что не попало ни в одну другую группу
    data object AllApps : GroupRule
    data class AnyOf(val rules: List<GroupRule>) : GroupRule
    data class AllOf(val rules: List<GroupRule>) : GroupRule
    data class Not(val rule: GroupRule) : GroupRule
}
```

`Unassigned` — важная страховка: пока в конфигурации есть хотя бы одна такая группа, новое приложение никогда не пропадает из вида молча.

Про `Category`: честная оговорка — `ApplicationInfo.category` заполнен далеко не у всех приложений (у большинства сторонних APK там `-1`), и там, где заполнен, часто врёт. Категории Play — это подсказка для первичной раскладки, а не надёжный механизм. В UI это будет названо «Разложить по категориям (приблизительно)».

### 1.3. Конфигурация по умолчанию

Первый запуск не должен требовать вообще никаких решений:

```
[верхняя зона: часы]
Избранное        (FAVORITES, пусто, подсказка «перетащи сюда»)
A–D  E–H  I–M  N–R  S–Z   (AlphaRange, LIST_COMPACT)
Прочее           (Unassigned — сюда падает всё нелатинское и новое)
```

Русские названия: буквенные группы работают по правилу «первая буква после нормализации», кириллица попадает в «Прочее». Как только пользователь ставит русскую локаль, дефолт меняется на кириллические диапазоны (А–Д, Е–К, …) плюс латинские. Это делается генератором дефолта, а не хардкодом.

## 2. Слои и модули

```
:app                — Application, HomeActivity, DI-граф, навигация
:core:model         — доменные типы, без Android-зависимостей
:core:data          — Room, DataStore, репозитории
:core:platform      — обёртки над LauncherApps, AppWidgetHost, NotificationListener, IconCache
:core:designsystem  — тема, типографика, атомы UI
:feature:home       — главный экран, рельс, группы, жесты
:feature:search     — поиск и провайдеры
:feature:settings   — настройки, редактор групп
```

Больше модулей на старте не нужно: они дают выигрыш на времени сборки и на дисциплине зависимостей, но каждый лишний — это накладные расходы на конфигурацию Gradle.

### Технологические решения и почему именно так

| Решение | Выбор | Почему |
|---|---|---|
| DI | Ручной граф (`AppContainer`), без Hilt/Koin | Лаунчер — один процесс, один жизненный цикл, десяток синглтонов. Hilt тянет ksp, кодогенерацию и рефлексию инициализации на старте; выигрыш от него здесь нулевой. |
| БД | Room + Flow | Реактивные запросы бесплатно, миграции честные. |
| Настройки | DataStore (Proto) | Типизировано, без рефлексии, асинхронно. |
| Загрузка иконок | Собственный `IconCache` | Coil/Glide заточены под сеть и URL. Нам нужно: `LauncherActivityInfo.getBadgedIcon` → маска adaptive-icon → две растровые версии → LRU в памяти + LRU на диске. Это ~300 строк и полный контроль над временем старта. |
| Сеть | Нет | Веб-поиск — `Intent` в браузер. Ни OkHttp, ни Retrofit в проекте. |
| Изображения/анимации | Только Compose | Никаких Lottie. |
| Сериализация | kotlinx.serialization | Для правил групп и бэкапа. |

Итоговый список внешних зависимостей: Compose BOM, Room, DataStore, kotlinx-serialization, kotlinx-collections-immutable, androidx-core. Всё.

## 3. Навигация и жесты

Главный экран — **не набор экранов, а одно состояние**. Кнопка Home должна возвращать в исходное состояние мгновенно, без пересоздания активити.

```
HomeState(
  scroll: ScrollPosition,
  expandedGroup: GroupId?,
  overlay: None | Search | Rail(groupId, subgroupId?) | AppMenu(componentKey) | Editor
)
```

### Карта жестов

| Жест | Действие |
|---|---|
| Свайп вверх от нижнего края | Поиск (поле + клавиатура снизу) |
| Тап по группе | Раскрыть/свернуть (эксклюзивно) |
| Палец на рельсе, ведение вертикально | Предпросмотр группы (таблетка), список неподвижен |
| Отпустить на рельсе | Раскрыть выбранную группу |
| Сдвиг влево, не отпуская | Выехали подгруппы; отпустил на подгруппе — раскрылась она |
| Долгое нажатие на приложении | Меню: шорткаты, инфо, в избранное, в архив, удалить |
| Долгое нажатие по фону | Настройки лаунчера / виджеты / обои |
| Двойной тап по фону | Настраиваемое действие (по умолчанию — блокировка экрана; требует Accessibility или Device Admin — см. 02-PLATFORM) |

Все жесты корневого уровня обрабатываются **одним** `pointerInput` на корне (`GestureRouter`), а не вложенными детекторами. Вложенные детекторы в Compose дерутся за события, и отладка этого стоит дороже, чем сразу написать один диспетчер.

### Про системный «назад»

Рельс живёт в полосе с отступом от края (≈24dp), поэтому системная зона «назад» не отбирается вообще. Это осознанная плата: чуть меньше удобства попадания в обмен на то, что жест «назад» на главном экране работает как везде.

## 4. Производительность

Лаунчер — единственное приложение, к которому пользователь возвращается по сто раз в день, и единственное, чьи 200 мс задержки воспринимаются как «телефон тормозит».

### Бюджеты (проверяются на S23 Ultra, 120 Гц → кадр 8.3 мс)

| Метрика | Цель |
|---|---|
| Холодный старт до первого кадра | < 400 мс |
| Нажатие Home при живом процессе | < 50 мс до готового кадра |
| Кадр при прокрутке списка | без пропусков на 120 Гц |
| Резидентная память | < 150 МБ при 250 приложениях |
| Фоновая активность в простое | нулевая: ни сервисов, ни таймеров, ни WorkManager |

### Как это достигается

- **Индексация приложений — не на старте UI.** Первый кадр рисуется из Room; обновление индекса из `LauncherApps` идёт после первого кадра, в фоне. Дальше — только инкрементальные обновления через `LauncherApps.Callback`, никаких периодических пересканирований.
- **Иконки — двухуровневый кеш.** Память (LRU) + диск (сжатые растры нужного размера). Декодирование 250 adaptive-иконок в первый кадр — гарантированные полсекунды, поэтому в первый кадр идут кеш и плейсхолдеры.
- **Baseline Profile + Startup Profile** с первой недели, не «когда-нибудь потом». На старте лаунчера это даёт 20–30% и его нельзя добавить в конце, не переделав сборку.
- **R8 full mode**, ресурсы shrink, никаких debug-веток в релизе.
- **Стабильность Compose:** все модели — `data class` с immutable-коллекциями, `key` в `LazyColumn` — `componentKey`, никаких лямбд, пересоздаваемых на каждой рекомпозиции.
- **Активити не пересоздаётся** при смене темы, обоев, локали: `configChanges` обрабатываются Compose-слоем.
- Замер — `Macrobenchmark`-модуль с тестами старта и прокрутки, запускается перед каждым релизом.

## 5. Визуальный стиль

Раз решение оставлено за мной — фиксирую, чтобы не переспорить самих себя через месяц:

- **Типографика первична.** Список — это текст, набранный с ритмом; иконки поддерживают, а не доминируют. Крупные, хорошо читаемые названия; иконки в компактном списке 32dp, монохромные по умолчанию, если приложение отдаёт monochrome-слой.
- **Ноль хрома.** Никаких карточек, рамок, теней и разделителей. Группировка — воздухом и весом шрифта.
- **Цвет — от обоев.** Динамическая палитра Material You включена по умолчанию (на 31+ работает штатно), с возможностью зафиксировать свою.
- **Тёмная тема — первого класса**, не инверсия светлой. Настоящий чёрный как опция (AMOLED S23 — это экономия батареи, а не украшение).
- **Анимации короткие и прерываемые.** 150–200 мс, spring, всегда можно перехватить пальцем. Длинная красивая анимация в лаунчере — это раздражитель с третьего дня.

## Пересмотр решения о хранилище (2026-09-08, фаза 1)

**Было записано:** Room + Flow для всех сущностей.
**Сделано:** один JSON-документ в DataStore, `kotlinx.serialization`.

Причина не в сложности Room, а в том, что задачи для СУБД здесь нет:

- Хранить нужно только решения пользователя — группы, ручные включения
  и исключения, настройки видимости. Это десятки групп и сотни членств:
  весь документ помещается в память целиком и читается один раз при старте.
- Список установленных приложений в хранилище **не попадает вообще**. Он
  берётся из `LauncherApps` за единицы миллисекунд, а его копия на диске —
  это только лишний источник рассинхронизации после установки и обновления
  приложений.
- Ни одного запроса, который выиграл бы от SQL, в продукте нет: состав группы
  считается по правилу в памяти (`GroupComposer`), и это единицы миллисекунд
  на 250 приложениях.
- Уходит KSP со всей кодогенерацией — это время сборки и время старта.
- Экспорт и импорт конфигурации (фаза 3) становятся тем же самым форматом,
  а не второй, расходящейся с первой, реализацией.

**Что за это заплачено:** нет автоматических миграций схемы. Взамен —
поле `version` в документе и ручные миграции при изменении формата. Для
JSON это проще, чем SQL-миграции, но забыть про него нельзя: конфигурация
пользователя обязана переживать обновление приложения.

**Когда решение придётся пересмотреть:** если появится сущность с историей
(журнал запусков для сортировки по частоте, кеш содержимого для поиска),
у которой много записей и нужны выборки по диапазону. Тогда БД добавляется
именно для неё, а конфигурация остаётся в JSON.
